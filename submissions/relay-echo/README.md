# relay-echo

The witness-sending entry, made fast. The witness is relayed whole and echoed back for checking:
a node's proof carries its children's signed proofs, and the verifier recomputes every chain of
the stream. It keeps [witness-baseline](../witness-baseline)'s certificate, proof format and
claim, and replaces only the compiled code of the verifier and the prover.

## How it works

- **The certificate is the core library's.** `lean/FastDefs.lean` defines a new decision
  `check'`, and `lean/FastSpec.lean` proves `check' = WitnessSending.check`, so
  `lean/Solution.lean` moves `RecursionFast.Library.WitnessSending`'s certificate to the new
  verifier: knowledge error 0, completeness error 0, no oracle query, fuel `8 · t`.
- **The verifier** decides what the library's does, faster:
  - the chain runs on four 64-bit words per digest, the padded block built directly in lanes;
  - each level of the proof is read in place from the byte array, then re-encoded and compared
    with the proof, which rejects any non-canonical input as the library's re-encoding does;
  - Keccak-f[1600] runs on complemented lanes, its first and last rounds written out and the
    rounds between them as a loop;
  - the chain's steps and the rounds within them are one loop over unboxed words, with no state
    allocated between steps.
- **The prover** (`prover/prover.s`) writes the same witness-sending proofs as the baseline's
  prover, with one of five Keccak-f[1600] kernels (`avx512vl`, `avx512vln`, `avx512`, `bmi`,
  `scalar`), each behind `cpuid`, timed in `prover setup` and re-checked against the scalar one by
  every request. `avx512vl` runs two chains per call, so step 1's two chains take one chain's time
  in one thread. The encoding, signatures and file write overlap with the chain on helper threads,
  which stay off the chain thread's core where sysfs shows the CPU topology.

## Why it is still slow

A node's proof contains every earlier proof, so each check recomputes about `Σ_{j≤i} n_j`
permutations: 32 M by step 96. This entry makes each of them about three times cheaper than
witness-baseline (#7) does (3.1 to 3.2 times locally; 2.6 to 3.5 on the evaluation machine,
estimated) and the proof parse almost free, but the verifier still grows with the stream and
dominates both scores. `NOTES.md` has the measurements (local, not from the evaluation machine),
the estimates for the evaluation machine and the dead ends.

## Files

| Path | What |
|---|---|
| `claim.json` | the declared numbers, the baseline's |
| `lean/Solution.lean` | the certificate, transferred along `V'_eq` |
| `lean/FastDefs.lean` | the verifier: the chain in lanes, the format on byte arrays, `check'`, `V'` |
| `lean/FastSpec.lean` | the equations L1, L2, L3 and L5, ending in `check'_eq` and `V'_eq` |
| `lean/FastSpecPerm.lean`, `lean/FastSpecLoop.lean`, `lean/FastSpecParse.lean` | the statements behind the permutation (L1), the chain loop (L3) and the format (L5) |
| `lean/FastProof*.lean` | byte-level lemmas for those proofs |
| `prover/prover.s` | the prover, GNU assembly generated by GCC 15.2 from `src/prover.c` and filtered for binutils 2.42 (`src/regen.sh`) |
| `src/` | the prover's C source, the generators of its kernels (`gen_*.py`, which write `keccak_*.inc`), the baseline's prover as the tests' reference (`ref_prover.c`), and the tests (`test.sh`) |
| `NOTES.md` | idea, results, what failed, what to try next |
