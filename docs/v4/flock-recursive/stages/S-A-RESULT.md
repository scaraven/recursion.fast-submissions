## 0. Normative constants (BP-E-M8)

The blueprint left β and α open; S-A fixes them. The same table, with KATs in hex limbs for the
Rust prover, is in `S-A-JOURNAL.md` §"Normative constants".

| Object | Value | Byte encoding |
|---|---|---|
| base field | CompPoly `BF64 = GF(2)[x]/(x^64 + x^4 + x^3 + x + 1)`, a 64-bit word, bit `i` ↔ `x^i` | 8 bytes, little-endian |
| **β** | **`x^63`** (word `0x8000000000000000`) | `00 00 00 00 00 00 00 80` |
| F | `BF64[y]/(y^2 + y + β)`, element `c₀ + c₁ y` | 16 bytes: `c₀` ‖ `c₁` |
| **α** | **`β y`** (`c₀ = 0`, `c₁ = 0x8000000000000000`) | `00×8` ‖ `00 00 00 00 00 00 00 80` |
| K | `F[u]/(u^2 + u + α)`, element `f₀ + f₁ u` | 32 bytes: `f₀` ‖ `f₁` |

Why: over this BF64 the only monomials `x^k` (`k < 64`) of absolute trace 1 are `x^61` and `x^63`;
every word below `2^61` has trace 0, so no "smaller" sparse choice exists. Multiplication by `x^63`
is one shift pair and one reduction (`B64.mulBeta`: `reduce (r <<< 63) (r >>> 1)`); `x^61` would
cost the same. Over F, `Tr(c₀ + c₁ y) = Tr_BF64(c₁)`, so `α = β y` has trace 1, and its product is
three `mulBeta` (`F.mulAlpha`: `α(z₀ + z₁ y) = β(β z₁) + β(z₀ + z₁) y`). **kernel**:
`FR.B64.frobSum_beta`, `FR.F.frobSum_alpha` (the traces), `FR.beta_eq_x_pow` (β = x^63).

(`f128_irreducible`, `f256_irreducible`), and `not_irreducible_one` shows the trace hypothesis

`equivBF256`).

## 5. Deviations from the blueprint

1. **β and α chosen** (§0): `β = x^63`, `α = β y`. The blueprint left them to `FRField128`
   (§2.1); BP-E-M8 asked S-A to fix them. **Blueprint change needed**: §2.1 and §1 should state
   them, and D-9′ should read `y² + y + x^63`, `u² + u + x^63 y`.
2. **The product variant is h32** (spartan-srom's `clmul32` Karatsuba), not h64 (BearSSL `bmul64`
   with bit reversal). h64 was 2–5 % faster in phase 0 (23.7 against 25.2 ns per GF(2^64) product)
   but needs a new proof (the reversal identity `rev(rev a · rev b) >> 1` = the high half, and the
   column bound 16 at positions 60–63 of `bmul64`). The measured F product is dominated by
   reductions and the result object, so the gain would be about 1–3 ns of 81. Left as an option
   for a golf pass (open question 1).
3. **Lazy reduction in `F.mul`**: three reductions instead of four, proved at the level of
   polynomial classes (`mul_c₀`, `mul_c₁`), not by composing `B64` products.
4. **`FRFieldBase` imports core only** (spartan-srom's imported `BF64.Bytes`, unused there);
   `FRFieldBaseCorrect` imports it instead. `B64.mul` is now `reduce ∘ clmul64` (the same word
   operations as before, regrouped), and `Q_mul` is proved through `P_clmul64`.
5. **Bytes are stated as the concatenation of the `B64` codecs**, with round trips and
   `bytesEquiv`; the statement against CompPoly's `ByteCodec (Ext P)` is not made, because
   `CompPoly.Fields.Extension.Bytes` is outside the allowlist (as in spartan-srom). The `B64` level
   is tied to CompPoly's codec (`B64.toBytes_eq`, `B64.ofBytes_eq`).
6. **Controls**: §5.6 asks for "`mul_twin_kat` on 8 pairs; `inv_mul` symbolic; a wrong modulus is
   reducible (`y² + y` has a root)". Delivered: 8 pairs for each of F and K, symbolic inverse
   (`toExt_inv`) plus a KAT, and two reducible moduli (`y² + y` and the sharper `y² + y + 1`, trace
   0, with an explicit root).
7. Copied lines over 100 characters remain in `FRFieldBaseCorrect` (they are spartan-srom's).

## 6. Open questions
