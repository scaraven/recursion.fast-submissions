## Findings

### G6-R1 (should-fix): §4's "44,288 identical, 0 differ" counts auxiliary names that were never compared; `._f` definitions escape the check

- `check.py` drops every name that contains an auxiliary pattern. As a result:
  - only **25,193** names, the non-auxiliary ones common to both sides, are actually compared;
  - the figure 44,288 is 25,193 plus 19,095 auxiliary names whose hashes happen to match.
  - 689 auxiliary names differ, and they are silently excluded. Most are `_proof_`/`_simp_` numbering shifts, which
    is harmless.
- Fifteen of those 689 are **`._f` definitions with the same type and a different value**, for example
  `FR.X.wLoop._f`, `FR.X.stepLoop._f`, `FR.X.walkLoop4._f` and `FR.X.segIR_sem._f`. These hold the computational
  content of a recursive definition. The parent's hash refers to them by name only. The shallow check cannot see a
  change in them.
- Two other gaps in the shallow check:
  - `Expr.hash` ignores `BinderInfo` (explicit or implicit) and binder names;
  - the hash does not include `levelParams`.
- The deep check above closes these gaps for `Solution`'s closure: 22,533 constants, 0 differ. So none of this is an
  actual change. Off the path (the controls, 118 modules), only the shallow check applies.
- **Fix:**
  - correct §4's wording: 25,193 compared, 0 differ; 689 auxiliary names excluded; the deep check gives 0 differ on
    the path;
  - before `check.py` is used again as the guard for later stages, make it fold auxiliary constants into their users
    and hash `BinderInfo`. The fold is about 40 lines of probe code, in the reviewer's scratchpad (`deep.tail`).

### G6-R2 (minor): `check.py` does not report names that appear or disappear

- `post` compares only the names that occur in both hash files. A constant that disappears, or a new one, is not
  flagged.
- §4's 16 names only at HEAD and 20 only now were computed separately. The reviewer's recount matches them exactly.
- Add the two set differences to `check.py`'s output, and freeze when they contain an unexpected name.

### G6-R3 (minor): the RESULT's provenance needs tightening

- The RESULT names HEAD `c82be25`; the worktree HEAD is `4537909`. No `lean/` file changed between the two
  commits, so this only needs the header fixed.
- `hash-head.txt` dates from 07:01, after iter1's merge (06:51). It was made from `fr-build-FEL`, whose `src` points
  into the worktree. It is still HEAD's data: R1's G6h reproduction confirms it. §4 should say it was cross-checked
  against `fr-build-G6h`, or regenerate it there.

### G6-R4 (minor): stale references to deleted module names

None of these breaks a build. They mislead readers, and they will mislead the next agent that greps for a module:

- comments in `prover/*.rs`: 14 references, for example `FRShape4`, `FRSegment`, `FRVerifier4`, `FRVIR4At`,
  `FRNodeRows4Defs`, `FRBlake2sCircuit` and `FRNodeRows4AggChk`;
- `BLUEPRINT.md` (84) and `QUEUE.md` (10);
- `logs/fr-build-E1b/prof.sh`'s default `MODS`, with five deleted `FRVIRTpl*` modules;
- comments in two E1b probes.

Put the module map (§3.4 / `iter6.apply.json`) in `QUEUE.md`. Do not rewrite the prover comments now; that is out of
G6's scope.

### G6-R5 (minor): friction for later stages from merged files

- Files now run up to 2,474 lines. The reviewer found no per-file cap in the harness: the comparator has 14 GB and
  1 h per step. The peak RSS of the clean build fell, from 4.8 to 3.97 GB.
- The cost falls on later work:
  - editing one member re-elaborates its whole target file, and every file that imports it;
  - low-level modules now pull large importers' dependencies with them. For example, `FRShape4` now lives inside
    `FRSoundness4Pos`.
- A later stage that edits a member must:
  - edit it inside its `section G6_<member>`;
  - keep the wrapper;
  - re-run the (strengthened) hash check.
- The `autoImplicit` hazard in RESULT §6.3 stays live.

### G6-R6 (minor): two stray controls are still outside `FR`

- `FRSoundness4P4aCtrl3` and `FRSoundnessFrChain` are not imported by `FR`. The same was true at HEAD.
- G6 builds them explicitly, but a plain `lake build FR` does not.
- Importing them from `FR` would make the controls' build complete by default. This is not G6's regression.

## Verdict

**Accept: no blockers.** The deep hash check shows that the merge changed no statement and no definition on the
certificate path:

- 22,533 constants, 0 differ;
- auxiliary constants folded into their users;
- binder info and universe count included;
- HEAD's side reproduced from a byte-identical HEAD tree.

`Solution.lean` is unchanged, the golfed proofs keep their statements, the controls moved verbatim, and the source
rule is clean. G6-R1 should be fixed in the RESULT's wording and in `check.py` before that check is relied on as the
guard for later stages. The rest are minor.
